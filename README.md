# سامانه مدیریت پروژه‌های بخش امنیت پژوهشگاه

پیاده‌سازی اولیه (MVP) سامانه‌ی یکپارچه‌ی مدیریت پروژه‌ها و منابع بخش امنیت، بر اساس سند نیازمندی‌ها. این نسخه با Django ساخته شده و شامل مدل داده، فرآیند تصویب پروپوزال (BPMN)، تخصیص نیرو و مجموعه‌ای از گزارش‌های مدیریتی است.

## ماژول‌ها و موجودیت‌ها

- **پروژه** (`Project`): موجودیت محوری با کد، عنوان، نوع، کارفرما، زمان‌بندی، وضعیت اجرا (تعریف‌شده/در حال اجرا/متوقف/خاتمه‌یافته)، درصد پیشرفت، بودجه و مجری.
- **پروپوزال** (`Proposal`) + **نسخه‌های پروپوزال** (`ProposalVersion`) + **تصمیم‌های شورا** (`ProposalDecision`): فرآیند دو مرحله‌ای تصویب (شورای علمی پژوهشکده، سپس شورای پژوهشی پژوهشگاه) با نگهداری کامل سابقه‌ی نسخه‌ها و نظرات/دلایل رد.
- **سربازان** (`Soldier`)، **همکاران داخلی** (`InternalCollaborator`)، **همکاران خارجی** (`ExternalCollaborator`): سه نوع نیروی انسانی با فیلدهای اختصاصی خودشان.
- **تخصیص نیرو** (`Assignment`): رابطه‌ی چندبه‌چند فرد–پروژه با سهم زمانی (درصد مشارکت)، از طریق `GenericForeignKey` برای پشتیبانی از هر سه نوع نیرو.
- **مجری پروژه**: طبق توصیه‌ی سند، به‌عنوان یک نقش روی پروژه/پروپوزال مدل شده (فیلد `executor` با `GenericForeignKey` به همکار داخلی یا خارجی)، نه یک موجودیت مستقل.
- **پژوهشکده** (`ResearchInstitute`): مرجع سطح اول تصویب.

## فرآیند تعریف پروژه

ماشین‌حالت پروپوزال در `Proposal` (فایل `projects/models.py`) پیاده‌سازی شده است:

`ارسال‌شده → در حال بررسی در پژوهشکده → (تأیید) در حال بررسی در پژوهشگاه → (تأیید نهایی) تأییدشده → صدور حکم مجری → در حال اجرا`

- تصمیم «نیازمند اصلاح» در هر شورا، پروپوزال را به مجری برمی‌گرداند؛ اصلاحیه‌ی پس از شورای پژوهشکده به همان شورا و اصلاحیه‌ی پس از شورای پژوهشگاه مستقیماً به همان شورا بازمی‌گردد (`resubmit_after_revision`).
- تصمیم «رد» در هر مرحله، فرآیند را متوقف می‌کند.
- تأیید نهایی در شورای پژوهشگاه و صدور حکم مجری (`issue_executor_order`) به‌صورت خودکار موجودیت `Project` مرتبط را می‌سازد.
- هر تغییر نسخه و هر تصمیم شورا در جداول جداگانه ثبت و نگهداری می‌شود تا روند بررسی کاملاً قابل پیگیری باشد.

## نقش‌ها و دسترسی

چهار گروه کاربری مطابق سند از طریق دستور مدیریتی ایجاد می‌شوند:

```bash
python manage.py setup_roles
```

گروه‌ها: «مجری»، «کنترل پروژه»، «مسئول ورود داده»، «ادمین کل سامانه». دسترسی به هر گزارش با دکوریتور `role_required` در `projects/permissions.py` کنترل می‌شود و کاربر مجری تنها به پروژه‌ها/گزارش‌های خودش دسترسی دارد.

## گزارش‌ها

تمام گزارش‌های مذکور در سند به‌صورت نمای وب (`projects/views.py` و قالب‌های `projects/templates/projects/`) پیاده‌سازی شده‌اند: وضعیت کلی پروژه‌ها، پیشرفت پروژه‌ها، پروژه‌های دارای تأخیر، شناسنامه‌ی پروژه، پروپوزال‌های در جریان، نرخ تصویب، میانگین زمان تصویب، ترکیب نیروها، بار کاری افراد، ظرفیت آزاد، پایان خدمت سربازان، قراردادهای همکاران خارجی، عملکرد مجریان و داشبورد مجری.

## راه‌اندازی محلی

```bash
pip install -r requirements.txt
python manage.py migrate
python manage.py setup_roles
python manage.py createsuperuser
python manage.py runserver
```

سپس با کاربر ادمین وارد شوید تا داده‌های اولیه (پژوهشکده‌ها، نیروها، پروپوزال‌ها) را از طریق پنل مدیریت (`/admin/`) ثبت کنید و گزارش‌ها را در آدرس ریشه (`/`) مشاهده کنید.

## تست‌ها

```bash
python manage.py test projects
```

تست‌ها ماشین‌حالت پروپوزال (مسیر تأیید، اصلاح در هر دو سطح، رد)، محاسبه‌ی درصد تأخیر پروژه، اعتبارسنجی سهم زمانی تخصیص و کنترل دسترسی نقش‌محور را پوشش می‌دهند.
